## Task 0: Perf baseline tests (P-IDLE, P-SELF)

**File:** new `tests/perf.spec.js`, tag `@perf`. Add a helper `countMutations(page, ms)` in `tests/helpers/perf.js`. It installs a MutationObserver (childList, subtree, characterData, attributes) on `document.body`, waits `ms`, and returns `{ batches, records, own }`, where `own` counts records whose target is inside `#rmd-popover`, `#tl-score-panel`, `.qc-badge`, the QC panel, or `.tl-toast`.

Tests:

1. **QC idle:** `bootQC(page, COMPARE_DATA)`, then `countMutations(page, 2000)`, expecting `batches === 0`. *Fails today: about 9–10 batches.*

   **Start counting only once the row has fully settled.** After a row loads, the lazy-load re-check can re-read the row up to 2 times over about 2.5s. Those re-reads are legitimate and must not count as idle churn. So wait until the QC verify timer is idle, using a test-only `window.__tlQcVerifyPending` flag set while a verify is scheduled, before counting. If a flag is not practical, wait a fixed 3s instead, and note that choice in the ledger.
2. **Composer typing:** on the annotation fixture, open the composer, type 20 characters into `#rmd-edit`, and wait 600ms. Expect `window.__tlSettleScheduled.remark === 0` and `window.__tlSettleScheduled.score === 0`, since nothing outside our own UI changed. Also expect the remark text to equal what was typed. *Fails today: about 20 each.*

   The counter is test-only: the settle code increments `window.__tlSettleScheduled[name]` each time it (re)starts a settle timer, but only if the test has created `window.__tlSettleScheduled` first; production never creates it. Debouncing hides the problem in a run count, so count schedules, not runs.

   Until T2 adds `Utils.observeSettled`, add the counter line directly in each module's `onMutate` (one line each, removed again in T2).

Commit only tests 1 and 2, marked `test.fail()` with a comment `// fixed in T1/T2`. T1 and T2 remove the `test.fail()`.
