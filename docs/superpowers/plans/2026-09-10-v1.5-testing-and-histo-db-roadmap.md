# v1.5 Roadmap: Test Infrastructure + Module 4 (Histo_DB)

> **This is a scoping roadmap, not an executable task-by-task plan.** It
> covers two independent subsystems (test infrastructure; a new Module 4
> feature) that got grouped together only because their prior-art lives on
> two now-archived branches (`testing`, `feat-Histo_DB`). Per
> `superpowers:writing-plans`' own scope-check rule, independent subsystems
> get independent plans — each section below ends with an explicit
> "next step" pointing at the brainstorming pass that should happen
> *before* a real, no-placeholder implementation plan is written for it.
> Treat this doc as the thing to hand to that brainstorming session, not
> as something to execute directly.

## Why this doc exists

Both subsystems already have real, substantial prior art sitting on local
branches that predate the `v1.4.0` module split and were never merged:

- **`testing`** (tip `92021cd`) — a pytest + Playwright suite plus a design
  rationale doc (`tests/TESTABILITY.md`) built against the pre-split,
  single-file script.
- **`feat-Histo_DB`** (tip `c1e08a2`) — reference material for Module 4
  ("Single-model Reference"): a detailed spec section in
  `work-KB/AGENTS.md` §4.4, plus two large exported-spreadsheet CSVs that
  are the offline data source for the module's lookup file.

Neither branch was deleted outright (see the `re-1.3.1`/`feat-v1.3.2`/
`claude/readme-debugging-cd3e68` archival pass earlier in this session) —
they're kept as-is specifically so a future session can pull the exact
content cited below with `git show <branch>:<path>`.

## Part A — Restoring test infrastructure

### What's salvageable, and what needs to change

The `testing` branch's suite is good *design*, not directly runnable code —
it targets a single `.user.js` file with a guarded
`if (window.__ASS_TEST__) { window.__ASS = {...} }` export at the bottom,
reached via `page.add_script_tag(path=".../annotation-scoring-shortcuts.user.js")`.
That export no longer matches reality: the script is now five separate
`src/*.js` files loaded via `@require`, each already publishing its own
public surface onto `window.TL` unconditionally (`TL.Utils = Utils`,
`TL.TransCursor = TransCursor`, `TL.ScoringShortcuts = ScoringShortcuts`,
`TL.RemarkComposer = RemarkComposer`, `TL.QCCompare = QCCompare` — see the
bottom of each `src/*.js` file).

**This is good news, verified in this session:** the old branch's entire
reason for a guarded test-only export was that the pre-split script was one
sealed IIFE with nothing reachable from outside it. That's no longer true —
`window.TL.Utils`, `window.TL.TransCursor`, and all three module factories
are *already* public, all the time, with no flag needed. A quick Node smoke
check this session (loading all five `src/*.js` files against a stubbed
`window`/`document`/`localStorage`, no jsdom or Playwright) confirmed
`TL.ScoringShortcuts(Utils)`, `TL.RemarkComposer(Utils, scoringShortcuts)`,
and `TL.QCCompare(Utils)` all construct cleanly and expose `.start`/
`.checkCompleteness` as expected. So:

- **No production code needs a test-only seam added.** Test code can call
  `window.TL.ScoringShortcuts(window.TL.Utils)` directly, exactly the way
  `annotation-scoring-shortcuts.user.js`'s own `bootAll()` does. The only
  thing genuinely not exposed is `bootAll()` and its three built instances
  (`scoringShortcuts`/`remarkComposer`/`qcCompare`) — those live inside the
  entry point's own closure. Whether tests need those instances (vs.
  constructing their own) is one of the open questions below.
- **`page.add_script_tag` needs to load all five files in `@require`
  order**, not one file — `utils.js`, `trans-cursor.js`,
  `scoring-shortcuts.js`, `remark-composer.js`, `qc-compare.js`, matching
  `annotation-scoring-shortcuts.user.js`'s own `@require` list — before
  either constructing modules directly or loading the entry point file
  itself to run the real `bootAll()`.
- **`TESTABILITY.md`'s actual analysis (Playwright vs. jsdom, what's
  testable vs. not) is unaffected by the split** and should carry forward
  close to verbatim — the reasoning (`getBoundingClientRect()` needs a real
  layout engine, `Selection`/`Range` boundary quirks need a real browser)
  is about the DOM, not the file layout.
- **Three of the four original test files need only mechanical updates**
  (fixture loading, not test logic):
  - `tests/test_trans_cursor.py` — `TransCursor` is pure logic, reachable
    unchanged via `window.TL.TransCursor(...)` instead of
    `window.__ASS.TransCursor(...)`.
  - `tests/test_check_mode_persistence.py` — the storage key
    (`trans-tool:nova-score-check-v1`) and the `Z`-cycles-mode behavior are
    both still exactly current on `main` (verified against
    `remark-composer.js`'s `SCORE_CHECK_KEY`/`CFG.keyCycleCheck` this
    session) — only the boot mechanism changes.
  - `tests/test_boot_smoke.py` — needs a rewrite of its assertions (there's
    no single `window.__ASS` object to enumerate keys on anymore), but the
    *goal* — "do all modules construct and `start()` without throwing,
    against a DOM with none of NOVA's real markup" — is if anything more
    valuable now that there are 5 files that can drift out of sync with
    each other, instead of 1.
  - `tests/fixtures/README.md`'s capture methodology (real markup, scrubbed
    content, provenance comments, never hand-author a fixture from the
    script's own selectors) is architecture-independent and should be
    adopted as-is.

### Open questions for a brainstorming pass (before writing a real plan)

1. **Python/Playwright vs. something else.** The `testing` branch chose
   pytest + Playwright because jsdom can't reproduce real layout
   (`getBoundingClientRect`) or `Selection`/`Range` quirks — both still
   apply today. Worth confirming this is still the right call rather than
   assuming it (e.g. a Node + Playwright JS suite would keep the whole repo
   single-language; the `TESTABILITY.md` reasoning should be re-validated,
   not just copied).
2. **Does the suite need `bootAll()`/instances at all**, or is
   constructing modules directly via `TL.*` factories (as this session's
   smoke check did) sufficient for everything except a true end-to-end
   "does the entry point boot correctly" test? If the latter still matters
   (and it does — it's the actual regression net for `@require` load
   order), the entry point file needs *some* seam, even if the module files
   no longer do.
3. **CI or local-only?** This repo has no CI configured. A suite that only
   ever runs manually still has value (this session leaned on
   `node --check` plus a hand-rolled smoke script for exactly this reason
   during the v1.4.3 refactor), but the `testing` branch's `pytest.ini` /
   `requirements.txt` should be reviewed against whatever the answer is.
4. **Fixture capture** — this needs a human with access to the live,
   authenticated `nova.xiaohongshu.com` site (an agent session can't log
   in), so the "captured, not hand-authored" fixtures described in
   `tests/fixtures/README.md` are a manual prerequisite step, not something
   a future coding session can do unassisted. Worth deciding up front how
   much of the suite (if any) blocks on that vs. ships fixture-free first
   (the pure-logic + boot-smoke + persistence tests need zero fixtures and
   are the obvious first slice).

### Recommended first slice (no design decisions required)

Port `test_trans_cursor.py` and `test_check_mode_persistence.py` essentially
unchanged (just retarget the loader at `window.TL.TransCursor` /
`window.TL.RemarkComposer`), plus a rewritten `test_boot_smoke.py` that
constructs all three module factories via `TL.*` directly (no entry-point
seam needed for this part) and asserts each has a `start` function and
starts without throwing against `blank.html`. This alone restores the
highest-value, zero-fixture-dependency portion of the old suite and doesn't
block on any of the four open questions above.

## Part B — Module 4: Single-model Reference ("Histo_DB")

### What's already spec'd

`work-KB/AGENTS.md` §4.4 on the `feat-Histo_DB` branch is a genuinely
detailed spec, not just a stub — it already covers:

- **Purpose & gating:** strictly read-only, active on every page (unlike
  Modules 1–3, which are URL-gated), useful only where the offline lookup
  file has a matching row for the batch's single-model translation.
- **UI:** an always-visible launcher pill (bottom-left, count badge once
  data loads) opening a floating panel — 8-direction resizable (not just
  corner-drag, unlike Scoring Shortcuts' width-only or Remark Composer's
  corner-only resize), draggable, with an adjustable font size. "Load"
  imports a `ref.json` file built offline by a separate Python tool
  (`build_ref_json.py`, not part of this repo) from exported spreadsheets —
  the two large CSVs committed on this branch are that offline source data.
- **The one fragile coupling:** the lookup key is the current translation's
  text run through `smNorm` (collapse whitespace runs, trim) — this
  normalization must match `build_ref_json.py`'s Python-side normalization
  byte-for-byte, since it's the join key between live-page text and the
  offline table. The spec explicitly warns against "improving" this
  normalization, since the match is already manually verified exact.
- **Deliberate deviation from the other three modules:** polls on a
  `700ms setInterval` rather than a `MutationObserver`, and rebuilds its DOM
  idempotently every tick (cheap since rendering is skipped while the panel
  is closed) rather than reacting to mutations — noted as intentional, not
  an oversight.
- **A specific persistence gotcha:** panel position/size saves must skip
  writing when the panel's measured width is under 100px, because a
  `display:none` panel reports a zero-width rect and would silently
  corrupt the stored size for next time.
- **Storage keys already chosen:** `sm_ref_data_v1`, `sm_ref_open_v1`,
  `sm_ref_pos_v1`, `sm_ref_font_v1` — note these don't follow this repo's
  established `trans-tool:nova-*` prefix convention (see README's "Storage
  keys" section) — worth deciding whether to rename to match before this
  ships, since nothing has been persisted under the old names yet on any
  installed copy.

### What's changed since that spec was written (needs re-validation, not blind porting)

- It predates the `v1.4.0` module split. The spec's own "Rewrite
  architecture" section (§5) describes a single outer IIFE with `Utils`
  built once near the top and each module as an inner function taking
  `Utils` as a parameter — that's exactly the shape `src/*.js` already has
  now, so Module 4 should become `src/histo-db.js` (or similar), following
  the identical `function HistoDB(Utils) { ... return { start }; }` /
  `TL.HistoDB = HistoDB;` pattern the other three files use, `@require`d
  from the entry point alongside them.
- It predates this session's `v1.4.3` Utils extraction (`Utils.makeDraggable`
  / `Utils.makeResizable`). The spec's "fully resizable (8-direction)"
  requirement is a superset of what `Utils.makeResizable` currently
  supports (corner/edge, width-and/or-height) — extending it to 8 directions
  (or scoping Module 4 down to corner-only, matching Remark Composer) is an
  open design decision, not a given.
- It predates the "modules stay behaviorally isolated" ground rule's
  current, tightened wording (README's "Ground rules" section) — worth
  explicitly confirming Module 4 fits the three sanctioned exceptions
  (`Utils`, `TransCursor`, `checkCompleteness()`) with no new one needed,
  since it's read-only and doesn't touch scoring at all.
- **The offline data is stale by construction.** The two CSVs on
  `feat-Histo_DB` are a snapshot from whenever that branch was cut
  (2026-08-22) — before building `ref.json` for real use, confirm whether
  fresher exports exist, since annotation batches move fast.

### Open questions for a brainstorming pass (before writing a real plan)

1. **Does `build_ref_json.py` exist anywhere**, or does it need to be
   written from scratch as part of this work? The spec treats it as an
   external, already-built tool ("not part of this script") — confirm
   before assuming it's just a porting exercise.
2. **Rename the `sm_ref_*` storage keys** to the `trans-tool:nova-*`
   convention, or keep them as-is? No user has anything stored under either
   name yet (Module 4 has never shipped), so this is a one-time free
   decision that gets much more expensive after the first real release.
3. **8-direction resize**: extend `Utils.makeResizable` to support it (and
   decide whether that's worth making generic vs. Module-4-specific), or
   scope the first version down to corner-only and revisit.
4. **How does a reviewer actually get `ref.json` onto their machine** and
   into the "Load" button — is that a manual step per reviewer, a shared
   file distributed some other way? Not covered in the existing spec.

### Recommended next step

This is a new, user-facing feature with real open product decisions (not
just implementation ones) — it should go through `superpowers:brainstorming`
properly before a `superpowers:writing-plans` pass, using
`work-KB/AGENTS.md` §4.4 (on `feat-Histo_DB`) as the starting spec rather
than starting from a blank page. Do not start writing `src/histo-db.js`
directly from this roadmap doc.
